Run a DIFF-ONLY pass of today's bot-corrections report(s) against the live CS v2
KB. This is a review-gate step — it must NOT push anything to v2 and must NOT
reindex.

Background: skills/bot-corrections/scripts/fetch_corrections.py already ran and
committed a report for each app that had new corrections since the previous
run, to reports/bot-corrections/<app>/<app>-corrections-<run-date>.md — a list
of corrections (question / bot's original_response / CS's corrected_response),
grouped by topic. This step only runs when at least one app has new
corrections — check `ls reports/bot-corrections/<app>/` and use the most
recent file (today's date) per app; skip an app entirely if it has no report
for today.

For each app that has a report for today (chatty, then joy):

1. Run `python3 skills/bot-corrections/scripts/prep_kb.py <app>` — caches the live
   KB to /tmp/bot-corrections-kb/<app>/ and prints the corrections report file used
   + the full KB file list.

2. Read the corrections report fully. For EACH correction item, find the matching
   KB file(s) in the cache (grep by topic/keyword) and classify:
   - COVERED — the KB already states the corrected fact accurately. This does NOT
     need a KB patch — flag it instead as a possible retrieval/reindex issue (a
     correction does not automatically mean the KB is wrong; the KB may just be
     stale in the index). Do not draft a patch for these.
   - OUTDATED — KB has stale/wrong content that contradicts corrected_response →
     quote the stale line + the correct line, name the file.
   - GAP — KB has no equivalent content at all → name the file the new content
     should go into.
   - PARTIAL — KB covers part but misses the specific point CS corrected → name
     file + the missing sub-point.
   Verify every candidate against the real cached file content — never assume.
   Only OUTDATED/GAP/PARTIAL get a patch.

3. For each OUTDATED/GAP/PARTIAL item, draft the FULL new file content (start from
   the cached file; edit in place for OUTDATED; add a new `## Section` at a real
   anchor heading for GAP/PARTIAL; match the file's existing voice/frontmatter).
   Write ONE correct example only — do NOT add a "don't say X" negative example
   (the bot can copy that negative text straight back to a customer). If multiple
   corrections land in the same KB file, merge all edits into one draft of that
   file before writing the payload entry.

4. Write a payloads file — JSON array of {agent, path, content}, one entry per
   changed file — to:
   reports/analysis/bot-corrections-<app>-<report-date>-payloads.json
   Skip writing a payloads file for an app with zero OUTDATED/GAP/PARTIAL items.

DO NOT call POST /api/kb/file or /api/kb/reindex yourself, and do not run
push_kb.py. Diff + draft only — Liz reviews and pushes herself.

When both apps are done, send ONE Telegram digest to Liz:
  python3 ~/CSL/skills/_shared/notify_tele.py --job "Bot Corrections — KB diff" \
    --status ok --summary "<digest text>"
The digest (summary arg, plain text, Telegram truncates ~1500 chars) should have,
per app: counts (# COVERED-possible-reindex / # OUTDATED / # GAP / # PARTIAL), the
top 3-5 items ranked by how impactful the fix looks, and the payloads file path(s)
— plus the exact command to push after she approves:
  python3 ~/CSL/skills/kb-sync/scripts/push_kb.py <payloads.json>
If an app has nothing to patch, just say so in one line for that app.

Do not commit reports/analysis/*-payloads.json (gitignored, temporary — deleted by
push_kb.py after a successful push).
