## Cần sửa (OUTDATED)

### 1. `kb/case/vip-tiers.md` — "no self-serve toggle to re-sync tier points" is now imprecise
- **Stale line** (line 123): *"There is no self-serve toggle to re-sync tier points to a new balance."*
- **Correct line to add right after it**: For a **processing-delay** glitch (e.g. a high volume of queued Place Order transactions), merchants now have a self-serve **"Recalculate VIP Tier"** button directly in the app dashboard — no escalation needed for that case. The **"no self-serve toggle"** statement still holds specifically for **re-importing/recalculating lifetime tier points from an external source file** after a bulk reset — that case still needs escalation.
- **One-line fix**: Add a clarifying bullet distinguishing "processing-delay self-serve fix" from "bulk-reimport-from-file escalation," so agents don't tell every merchant with a tier-lag issue to wait for backend intervention when a self-serve button exists.

### 2. `kb/reference/translations.md` — "two routes reach the same underlying widget strings" overstates coverage
- **Stale line**: *"Two routes reach the same underlying widget strings — either works: [Settings → Translations → Widget design surface] or [On-site content → Widget → Widget design → Setup → Content & Translations]."* This is presented as the complete picture of where widget/loyalty text lives.
- **Correct line to add**: A **third, separate location** — **Settings → Translations → Storefront blocks** — holds the translation fields specifically for **Loyalty Hub (account page)** content, and it does **not** automatically share values with the widget/loyalty-page translation fields above. The same conceptual field (e.g. a program's description, "Show more"/"Show less") can genuinely show 3 different values across widget / loyalty page / Loyalty Hub because each surface pulls from its own field — this surfaced as the single largest support thread this week (one merchant, ~150+ messages) precisely because two different agents didn't know about the third location.
- **Occurrence count verified**: searched the full cached `translations.md` for "Storefront blocks" — **0 occurrences**. Confirmed genuine gap, not a wording issue.

## Cần bổ sung (GAP/PARTIAL)

### `kb/reference/redeeming-programs.md`
- **GAP** — under "Redeem value modes": add that **Dynamic Discount** (flexible point thresholds) is itself a **paid-plan feature** — Starter (free) can only use **Fixed Discount**. A merchant on Starter wanting multiple redemption levels must create several separate Fixed Discount programs.
- **GAP** — under "Discount types" (BXGY): add that a BXGY reward with **X's minimum quantity set to 0** still requires the customer to actively **redeem through the widget/loyalty page** first — simply adding the free item Y to the cart does not auto-apply it. Also note the **default selection mode for multi-item Free Gift programs is "Free one product from selection"** (pick 1), not all items, unless explicitly switched to "Free all products in selection."

### `kb/reference/points-advanced.md`
- **PARTIAL** — under "Adjusting a customer's points has a floor of 0": this floor applies to **manual admin adjustments only**. Add a bullet clarifying that **automatic Anti-Cheat deduction** (auto-revoke-on-refund/Refund Points toggle) can push a balance **below 0** if the customer already redeemed the points before the refund/cancellation happened — expected behavior, not a bug, distinct from the manual-adjustment floor.

### `kb/reference/vip-tiers.md`
- **GAP** — under "Exclusive Tiers" (Setup section): add that Joy **does not allow the store's first/base tier to be marked Exclusive** (Manual only) — new members land in the base tier automatically by default, which conflicts with Exclusive's manual-assignment model. Merchants building a paid/invite-only tier must keep a non-exclusive base tier and add the paid tier as a separate, additional tier.
- **GAP** — near "Tier Assessment" or as a new small section: document the self-serve **"Recalculate VIP Tier"** button for processing-delay cases (see OUTDATED item above, mirrored here for discoverability from the reference doc).

### `kb/reference/referral.md`
- **GAP** — new section: the **three referral email templates** and their exact triggers — **Referral invitation** (to friend, fires only with Automated email sharing on, when referrer clicks Send; link only, no coupon yet), **Coupons for referees** (to friend, right after they submit their email on the referral landing page — this is when their coupon is generated, independent of whether they ever order), **Reward for referrers** (to referrer, after friend's order reaches Paid). This exact confusion caused a multi-agent misfire this week (one agent incorrectly told a merchant the referee's coupon requires an order first).
- **GAP** — new section (privacy/fraud-detection detail): `avada-joy-geo` sessionStorage entry (IP/city/ISP from `geoip.apps.getjoy.ai`, Avada-owned) for fraud detection only; referrer identity in an AES-encrypted cookie; tracking pixel's `[customer_privacy]` flags are all `false` (fires before cookie-consent decision, no built-in delay option today).
- **GAP** — under "Referral limits" or "Anti-cheat": (a) no native setting requires a referrer to have made a prior purchase before referring; (b) referral rewards cannot be configured as cumulative/escalating (1st=$10, 2nd=$20 total, etc.) — only a flat reward per successful referral is supported.

### `kb/reference/integrations-other.md`
- **GAP** — add **Intercom** to the synced-fields comparison table alongside Chatty/Gorgias (loyalty reward data syncs to Intercom, confirmed working this week after a bug fix) — currently **0 mentions** of Intercom anywhere in the cached KB.

### `kb/reference/integrations-mobile.md`
- **GAP** — add a short note that **JMANGO360** (native mobile app builder) is explicitly **not supported** today (unlike the documented Shopney/Tapcart, which are Ultimate-only but supported) — logged as product backlog with no ETA, so agents don't need to re-investigate from scratch each time it comes up.

### `kb/reference/analytics.md`
- **PARTIAL** — under the metrics table: add a short explanatory note that **"Points redeemed" counts every point spent to generate a coupon**, whether or not that coupon is ever applied to a paid order — so it can look much larger than **"Revenue by Joy"**, which only counts orders where the discount was actually used. This gap is expected, not a data/tracking error, and came up as a merchant reconciliation question this week (465k points redeemed vs a much smaller assisted-revenue number).

### `kb/reference/migration.md`
- **GAP** — under "Data migrated" or as a new short note: clarify that migration only covers **customer data** (name, email, phone, tier name, birthday, status, point balance) — **program configuration itself** (earning rules, redeeming rules, VIP tier setup, widget design) is **not** transferable between two Joy accounts/stores and must be rebuilt manually on the destination store.
