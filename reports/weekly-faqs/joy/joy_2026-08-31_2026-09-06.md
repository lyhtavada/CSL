## 1. Getting Started / Launch

### Q1: We erased all points/history and want a clean launch — will existing members automatically get sign-up points at launch, or only when they log in?
**Frequency:** 1 session (multi-day, high-frustration escalation) 🆕
**Standard answer:** Sign-up points are never granted automatically "at the moment of launch" — they fire the **first time an existing customer logs in and the Joy widget renders** for them post-launch, not retroactively. If you want every existing member's balance at exactly 0 before that first login, resetting historical points to 0 (while keeping their point *history* intact) requires a **CSV import handled by the team** — it isn't a self-serve toggle, since a full points-balance reset isn't a built-in one-click feature. Plan for this a few days ahead of a hard launch date, especially around a national holiday when the team's turnaround is slower than usual.

### Q2: Can the team bulk-enroll customers into Joy membership via API from a third-party vendor, without them ever logging into the store?
**Frequency:** 1 session 🆕
**Standard answer:** No — there's no API to bulk-create memberships ahead of a customer's first login. Joy's standard flow is customer logs in → becomes a Member → gets assigned a tier; membership isn't pre-provisioned from an external system syncing customer records in bulk. If a third-party platform needs to drive enrollment, escalate with the exact flow they're proposing so the team can confirm what (if anything) is technically feasible today — don't promise a bulk API import.

### Q3: How do I properly test a new loyalty setup without affecting real customers or my live theme?
**Frequency:** ~4 sessions 🔁 recurring
**Standard answer:** Two separate controls, often needed together: (1) **Sandbox Mode** (Reward programs → toggle Sandbox on) stops real customers from earning/redeeming while you configure, and your own test email(s) go on the **Test list** so you can still earn/test while it's on; (2) to preview visual/theme changes without touching the live storefront, **duplicate your live theme**, enable the Joy app embed only on that draft theme, and test there. Sandbox controls *earning*, not *visibility* — it does not hide the widget from real visitors, so if you need the widget itself hidden during testing, use the duplicated-theme approach, not Sandbox alone.

## 2. Points — Earning

### Q4: A first (small) order didn't earn any points even though the earning rule is active and not excluded.
**Frequency:** 1 session 🆕
**Standard answer:** This can happen from **rounding down**, not a bug or exclusion. If the active tier's earning rate is denominated in a large currency unit (e.g. "1 point per 1,000,000 CLP spent"), an order below that threshold converts to a fraction of a point (e.g. 0.1), and Joy always **rounds down to 0** rather than up. Once the customer's cumulative spend crosses into a higher VIP tier with a richer rate, later orders convert normally. If a merchant reports "orders under $X never earn points," check the applicable tier's earning rate for this rounding effect before assuming a bug.

### Q5: How do I set up a decimal/fractional per-tier earning multiplier (e.g. 1.5×), and does it need Shopify Flow?
**Frequency:** 1 session (technical requirements doc) 🆕
**Standard answer:** The built-in **Bonus Points** tier perk only accepts whole multipliers (2×, 3×, 4×) — fractional rates need the **Rule Engine** instead: upgrade the earning program to Rule Engine (Reward programs → Earning programs → More actions), then add a Place order rule with the decimal rate, targeted either via "Who to reward → Only customers in a VIP tier" or a Rule Engine customer-segment condition. No Shopify Flow bridge is needed for this. Requires Advanced/Ultimate (Rule Engine) and an existing VIP Tier program.

### Q6: Can we run a scheduled bonus-points campaign (e.g. "double points this weekend") the easy way?
**Frequency:** ~2 sessions 🔁 recurring
**Standard answer:** Simplest path: temporarily edit the Place Order earning rate under Reward programs → Earning programs, then switch it back manually after the promo window. For an automated on/off schedule without manual toggling, use the **Rule Engine** (Advanced/Ultimate) with a date/time condition on a Place Order rule instead.

## 3. Points — Redemption / Discounts

### Q7: A discount code isn't stacking with another discount even though Combinations is enabled — is this a Joy bug?
**Frequency:** 1 session (multi-day troubleshooting) 🆕
**Standard answer:** Usually not a Joy bug — two **Shopify platform limits** commonly get mistaken for one: (1) on non-Plus stores, **only one manually-entered discount code** can be active in the cart at a time, regardless of the Combinations setting — Combinations governs stacking with *automatic* discounts and other discount classes, not stacking two entered codes together; (2) **two Product-level discounts can only combine when they apply to different line items** — if both target the same product, Shopify won't apply both even with Combinations on. Before escalating, confirm which of these two cases applies by checking whether the conflicting discount is a code vs. automatic, and whether it targets the same product as the Joy reward.

### Q8: A BXGY / Buy-X-Get-Y "free item" discount is making the more expensive product free instead of the cheaper one.
**Frequency:** 1 session (real bug, resolved) 🆕
**Standard answer:** By design, Shopify's BXGY discount applies the free-item discount to the **lowest-priced eligible item** in the "Customer gets" list, not the highest. If a merchant sees the opposite, the likely cause is a **previously-generated discount code that adopted the old program settings at the time it was created** — editing the program afterward doesn't retroactively update codes already issued. A newly-generated code will reflect the current (correct) settings; bulk-updating all previously-generated codes to match the latest configuration needs the team to run it as a backend batch job — flag this rather than promising it's automatic.

### Q9: Do I need to worry about a redeemed code being "double-deducted" for the same reversed/refunded order — once at refund, once at the expiry pass?
**Frequency:** 1 session 🆕
**Standard answer:** No — when an order is refunded, Joy creates a separate reversal entry immediately, and that original earning activity's usable-points value is zeroed out so the later expiry pass skips it entirely. A merchant reviewing raw export files (e.g. `customer-activities-expiring.csv`) may see the original row still listed, but the actual balance file confirms no further deduction happens.

## 4. Widget

### Q10: The widget/loyalty page shows in English even though the default language is set to another language.
**Frequency:** ~4 sessions 🔁 recurring
**Standard answer:** Check, in order: (1) is another translation app (Translate & Adapt, etc.) installed and connected only to the **live** theme while testing on a **draft** theme — a mismatch here makes Joy fall back to detecting the **browser language** instead of the translation app's chosen language; (2) was the change made under **Settings → Translations** (storefront-facing) rather than **Settings → In-app languages** (admin panel only — does not affect the storefront); (3) for text with no dedicated translation field (e.g. static popup copy), use the AI-powered **Translations → section editor** search box (the "Ask AI to edit text" field, not the plain keyword list) rather than assuming it can't be edited. If translations that were previously correct suddenly reset to English after a language was re-added, that's a rare confirmed bug under investigation — escalate rather than re-explaining setup steps to the merchant.

### Q11: Ways to Earn / Ways to Redeem sections on the loyalty page or widget show blank even though the app embed is enabled.
**Frequency:** 1 session (multi-day) 🔁 recurring
**Standard answer:** Check in order: (1) the earning/redeeming programs are actually **Active**, not just created; (2) auto-generated icons for Ways to Earn require **Essential plan or above** — on Starter, icons must be uploaded manually and won't appear on their own after upgrading without a hard refresh; (3) **Customer Eligibility** (Settings → General, not under Membership) isn't accidentally set to a manual/restricted mode. If all of these check out and it's still blank, this needs direct store investigation rather than repeating the same checklist.

### Q12: A staff account can't see Joy in Shopify Admin.
**Frequency:** 1 session 🔁 recurring
**Standard answer:** This is a standard Shopify Admin permissions issue, not a Joy setting — grant app access and customer-viewing permission under Shopify Admin → Settings → Users and permissions, the same as for any other app.

## 5. VIP Tiers

### Q13: We assigned VIP tiers manually, and after changing the points/threshold setup, the assignments "disappeared."
**Frequency:** 1 session 🔁 recurring
**Standard answer:** Not data loss — any change to a tier's threshold, calculation rule, or a relaunch triggers Joy to **re-run the tier assessment for every customer** against the new configuration. Customers who no longer meet the new (typically higher) threshold drop back to the lowest tier automatically. If a merchant wants previously-assigned tiers restored after this, that's a manual restoration request to the team, not an automatic revert.

### Q14: Can VIP tier maintenance be based on a rolling 12-month spend window (drop the tier if spend over the last 12 months falls below X)?
**Frequency:** 1 session (detailed technical requirements) 🔁 recurring
**Standard answer:** Yes — this is **Tier Assessment**, available on **Ultimate only** and requiring enablement by the Joy team on top of the plan gate (not self-serve, even on Ultimate). It supports an exact rolling window (Assessment cycle + offset + threshold). **Advanced** gets a simpler feature instead — **Tier level control** — which only demotes for pure inactivity (no qualifying activity in N months), not a spend/order/points threshold; it cannot do "keep tier only if spend ≥ $X over the trailing 12 months." Don't conflate the two when an Advanced merchant asks for rolling-window maintenance — they need to upgrade to Ultimate for that specific behavior.

## 6. Referral

### Q15: What is the exact Klaviyo variable to show the referee's/referrer's discount code (or store credit amount) in an email, and does "Referee Claim Reward" fire for the referrer or the referee?
**Frequency:** 1 session — extended over several weeks, ⚠️ **agents gave 3 different, contradictory variable names across replies** 🆕
**Standard answer:** Per the documented referral flow: the **referee** enters their email at the referral landing page and claims their own reward (coupon/store credit) at that step — this is exactly when the `Joy: Referee Claim Reward` event fires. The **referrer's** reward stays pending separately until the referee's order reaches Paid/Fulfilled (`Joy: Referral Friend Complete`). Any answer describing "Referee Claim Reward" as being about the *referrer* is incorrect and contradicts the documented flow — don't repeat it. **The exact Klaviyo event-property variable name for the coupon code/discount value carried by these two referral events is not currently documented and was not consistently confirmed across support replies this week** (three different formats were given: `{{ referee_discount }}`/`{{ referrer_discount }}`, and `{{ event|lookup:'reward'|default:'' }}`) — do not repeat any of these as verified until the team confirms one exact property name; escalate for confirmation rather than guessing.

### Q16: A referral discount code the referee received stopped working after a failed order retry — can it be un-stuck without regenerating everything?
**Frequency:** 1 session 🆕
**Standard answer:** If a customer's issued referral coupon can't be found in their discounts, or a code stops validating after a failed/retried order, this needs direct investigation with the customer's email and the exact code — collect both and escalate; there's no self-serve fix for a coupon stuck in this state.

## 8. Integrations

### Q18: We use Klaviyo to send a survey and want completing it (without the customer visiting the site) to award points — is there a trigger for that?
**Frequency:** 1 session 🆕
**Standard answer:** Not via Klaviyo alone — a Klaviyo trigger can only **send** an email/flow, it cannot **capture** survey-completion data back into Joy to award points. The only way to connect a survey completion to a Joy reward is through **Shopify Flow**: the survey tool must expose a Flow trigger (or the merchant uses an API/webhook bridge) that Joy's "Add point" Flow action can react to. If the survey app has no Shopify Flow trigger and no API, this isn't currently achievable.

### Q19: Does the Joy POS wallet-pass QR work with Shopify POS's own built-in scanner, or only Joy's in-app scan button?
**Frequency:** 1 session 🆕
**Standard answer:** Only Joy's own **QR scan function inside the POS extension** — the loyalty pass cannot be scanned using Shopify POS's native hardware/app barcode scanner. This has been this way since the feature launched (confirmed with the tech team), so if a merchant reports the loyalty pass "used to scan with the regular scanner but stopped," the likely explanation is they were previously using the in-extension scan button and the behavior hasn't actually changed — reinstalling the POS tile doesn't remove or restore this option since it was never available via the native scanner.

### Q20: Does Joy work with [Attentive / OneMobile / Trustpilot]?
**Frequency:** ~3 sessions (3 separate apps asked) 🔁 recurring
**Standard answer:** None of these three are currently supported: Attentive is not a supported email/SMS integration (Klaviyo, Omnisend, Mailchimp, Drip, Sendlane, PushOwl are), OneMobile is not a supported mobile-app integration (only Shopney and Tapcart, Ultimate-only), and Trustpilot is not one of the supported review apps for the Write-a-review program (Judge.me, Yotpo, Air Reviews, Fera, Loox, Review Rocket, Klaviyo Reviews, Okendo, Reviews.io, Growave, Stamped are).

## 9. Store Credit / Custom "Credit" Programs

### Q21: What's the actual difference between Joy Points and (Shopify) Store Credit, and can a custom-labelled point type (e.g. "GT Credit") behave like store credit at checkout?
**Frequency:** ~5 sessions this week (recurring confusion pattern) 🔁 recurring
**Standard answer:** **Points** are an abstract Joy currency redeemed for a discount coupon (manual step); **Store Credit** is Shopify's native cash-value balance, granted directly by select Joy programs (Place Order, Referral, Milestone) and auto-applied at checkout with no code needed. A merchant's own custom label for points (e.g. "GT Credit") is still **Joy points under the hood** — it does not gain Store Credit's auto-deduct-at-checkout behavior just by renaming it. The only way to get checkout auto-deduction is to actually configure the program's reward type as **Store Credit**; there's no way to make a custom-named points balance deduct directly at checkout without converting it. The **Write a Review** earning program does not currently support Store Credit as a reward type (only Place order, Referral, and Milestone do) — this is on the roadmap but not yet built; don't promise a timeline.

### Q22: Can I set up a pure cashback program (X% of order value back, not points-per-item)?
**Frequency:** 1 session 🔁 recurring
**Standard answer:** Yes, via **Store Credit** as the Place Order reward type — set the earning ratio so it approximates the desired percentage (e.g. "1 credit per €20 spent" for a 5% cashback rate). Two mechanics to flag to a merchant setting this up: the reward amount must be at least 1 whole store-credit unit per redemption (no $0.05 increments) unless **decimal store credit** is enabled for exact fractional amounts, and by default Joy **simplifies the displayed rate** to its lowest form (a "don't simplify" checkbox changes display only, not the actual math).

## 10. Pricing / Billing

### Q23: What happens if we exceed our plan's free monthly order quota — do we get auto-upgraded, or does the program pause?
**Frequency:** ~2 sessions 🔁 recurring
**Standard answer:** No automatic plan upgrade or downgrade happens based on order volume. On the **Starter** (free) plan specifically, exceeding the 250 free orders/month pauses point earning/redemption until the next 30-day cycle resets — the merchant is not billed or bumped to a paid tier. Paid plans (Essential/Advanced/Ultimate) instead charge a **per-100-orders overage fee** rather than pausing — see kb_pricing for the exact overage rate per plan.

### Q24: A bulk historical-order import inflated our usage-fee calculation — can imported/archival orders be excluded?
**Frequency:** 1 session 🆕
**Standard answer:** Yes, but not automatically — Joy counts **all** orders created in Shopify within the current 30-day billing cycle toward the usage fee, including bulk-imported historical/archive orders, unless those imported orders carry a distinct **tag** (e.g. "imported" or "archive"). If tagged, the team can exclude orders with that tag from the usage-fee count — the trade-off is that excluded orders also won't earn loyalty points. Recommend tagging archive imports going forward and asking the team to apply the exclusion before upgrading, to avoid a one-time inflated invoice.

## 13. Migration

### Q28: How do I migrate points/store-credit balances from Rise.ai (or another platform without a dedicated Joy guide)?
**Frequency:** 1 session 🆕
**Standard answer:** Use the **generic CSV route**: on the source platform, export customer data (name, email, phone) plus the balance to migrate; convert store-credit/balance figures to Joy points at whatever ratio you choose (commonly 1:1) and put that number in the Point Balance column; then upload via **Settings → Migration** once Essential+ and the migration tool are enabled by the team. **Gift cards cannot be migrated or imported** — Joy's migration only covers customer name/email/phone/VIP tier/birthday/status/point balance, not gift card data; if a merchant wants gift-card balances converted to points, they must calculate the equivalent points themselves and separately void/zero the original Shopify gift card so the balance isn't double-counted.

### Q29: My migration import shows the wrong total points for a customer — how do duplicate/disabled entries in the source export affect the result?
**Frequency:** 1 session 🆕
**Standard answer:** Migration imports **sum every matching row** for a customer's email in the uploaded file — if the export includes multiple rows per customer (e.g. raw activity history rather than a summarized current balance, or duplicated profile rows), each row gets applied as a separate migration action and the totals will overstate the real balance. Before uploading, the merchant should de-duplicate to one row per customer holding their **final, current** balance (removing already-expired/disabled point entries), not raw activity logs.

## 15. Edge Cases / Bugs

### Q31: A customer received a manually-added point adjustment, and it got silently reversed shortly after.
**Frequency:** 1 session (root-caused) 🔁 recurring pattern
**Standard answer:** When a manual point adjustment "bounces back," check whether the merchant has an external CRM or third-party system connected via **Joy's API keys** that syncs/adjusts point balances automatically — Joy's activity log will show the reversal as a **REST API** action (not a Joy-internal one) with a note like "Auto Update (CRM to Joy)" if this is the cause. This is the merchant's own external integration overwriting the manual change, not a Joy bug; the fix is on the merchant's side (reconfigure or retire the syncing system), and manual re-additions will keep bouncing back until that's resolved.
