## GAP / PARTIAL detail

### 1. GAP (highest priority) — Referral: Klaviyo coupon-code variable undocumented + "Referee Claim Reward" direction confusion
**File:** `kb/reference/referral.md` (also touches `kb/reference/integrations-email.md`, not patched — referral.md is the primary owner of referral-flow facts)
**Frequency signal:** 1 session, but spanning **weeks** of back-and-forth with **3 different agents giving 3 different, contradictory variable names**, plus one agent flatly mis-describing which side "Referee Claim Reward" applies to — directly contradicting the file's own Flow section. This is exactly the kind of contradiction the KB should prevent.
**What's missing:** `kb_referral.md`'s Flow section correctly states the referee claims their own reward at the landing-page step, and `integrations-email.md` correctly lists `Joy: Referee Claim Reward` as "the referred friend claimed their reward" — but neither file gives the actual Klaviyo **event-property variable name** for the coupon code carried by that event, which is the exact question every escalation in this thread was about. Because the fact isn't written down, agents guessed differently each time.
**Fix (this patch):** Add a **CS-critical callout** right after the existing "Two related Klaviyo/Omnisend events" paragraph in `referral.md`, restating in the strongest terms which side each event is about, and explicitly flagging that the coupon-code property name is **not confirmed** — so an agent reads "escalate for the real value" instead of inventing one. This does not fabricate a variable name (none of the three seen this week could be verified against the file), it only stops the misattribution and tells the agent not to guess.

### 2. GAP — Redeeming: Shopify's own discount-stacking limits aren't explained
**File:** `kb/reference/redeeming-programs.md`
**Frequency signal:** 1 session, but a multi-day thread (5+ round trips) that a one-paragraph KB addition would likely have resolved in the first reply.
**What's missing:** The `Combinations` bullet just says "which Shopify discount classes can stack" with no explanation of two well-known Shopify platform limits that get mistaken for Joy bugs: (1) only one **manually-entered discount code** can be active in a cart at a time regardless of Combinations, and (2) two **Product-level** discounts can only combine if applied to **different line items**.
**Fix:** Expand the Combinations bullet with these two sub-points.

### 3. GAP — Redeeming: BXGY "wrong item made free" + stale-code caveat
**File:** `kb/reference/redeeming-programs.md`
**Frequency signal:** 1 session (root-caused, real Joy-side confirmation needed), but this exact "why is the expensive one free" question is a recognizable pattern likely to recur.
**What's missing:** The BXGY discount-type line doesn't document that Shopify's BXGY discounts always target the **lowest-priced** eligible item, nor the caveat that a **previously-generated code** keeps whatever settings were live when it was created — editing the program later doesn't retroactively fix codes already issued (requires a team-run backend batch job to fix in bulk).
**Fix:** Add a short note under the BXGY discount type line.

### 4. PARTIAL — Wallet pass: staff-side scanning must use the Joy POS extension's own scanner
**Files:** `kb/reference/wallet-pass.md`, `kb/reference/pos.md`
**Frequency signal:** 1 session, but confirmed by the team as "worked this way since the beginning" — a fact worth having written down once rather than re-explaining per merchant.
**What's missing:** `wallet-pass.md`'s "Steps for staff at POS" section only covers the customer-facing add-to-wallet flow (customer scans a QR to *add* the pass). Neither `wallet-pass.md` nor `pos.md` documents the reverse action a merchant actually asked about this week — a staff member scanning an *already-added* wallet pass to look up a customer — and that Shopify POS's native hardware/app barcode scanner does **not** work for this; only the Joy POS extension's own in-app QR-scan button does.
**Fix:** Add one clarifying paragraph to `wallet-pass.md`'s POS steps section, and cross-reference from `pos.md`.

### 5. PARTIAL — Store credit: Write Review program can't award it yet
**File:** `kb/reference/earning-programs.md`
**Frequency signal:** 1 session, but store-credit-vs-points confusion touched ~5 sessions this week generally; this specific "why can't my review program give store credit" sub-case is a recurring shape.
**What's missing:** The earning-programs table lists "Place order — Points or store credit per purchase" but the Write review row doesn't say points-only. A merchant this week spent several turns discovering that only Place order, Referral, and Milestone currently support Store Credit as a reward type.
**Fix:** Add "(points only — Store Credit reward type is not supported here yet; in development, no ETA)" to the Write review row.
