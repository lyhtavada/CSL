## GAP / PARTIAL Detail

### Q14 — Custom Scenario silently overridden by a built-in Assistant skill (PARTIAL)
**File:** `kb/faq/train-ai.md`
**Where:** end of the "Step 4: Add Scenario Instructions" section.
**Why:** `train-ai.md` explains how to create a Custom Scenario, but nowhere warns that a **built-in Assistant skill covering the same topic** (e.g. After-sales support's return/refund handling) can win out over a merchant's own Custom Scenario or general instruction on the same subject. A real case this week ("don't offer to submit claims") needed the team to identify this exact conflict via Review Sources before the merchant's instruction actually took effect. This is a genuinely new failure mode, not previously documented, and directly actionable (check Review Sources → find the conflicting built-in skill → turn it off or edit the scenario).

### Q19 — Proactive Chat popup shows wrong content (a discount instead of the intended welcome message) (PARTIAL)
**File:** `kb/faq/proactive-chat.md`
**Where:** after the "Proactive Chat Templates" table.
**Why:** The file documents templates (Welcome visitors, Cart booster, etc.) and setup steps, but doesn't call out that picking the wrong template's message field is the most common cause of "my popup shows a discount/coupon instead of my welcome message" — a real, resolved case this week. Also worth documenting: proactive messages don't consume an AI conversation credit unless the customer replies, which came up as a related merchant question in the same conversation and isn't stated anywhere in the file.

### Q23 — Personal info exposed via an auto-generated FAQ answer (GAP, preventive note)
**File:** `kb/faq/faqs-page.md`
**Where:** new short subsection after "How to Set Up the FAQs Page."
**Why:** A merchant's home address was surfaced in an FAQ generated via Sync Store Page / Generate with AI. There's no existing guidance anywhere in the FAQ-related docs to review auto-generated content for accidental exposure of private information before publishing. This is added as a preventive best-practice note, not a bug-fix instruction — it doesn't invent any new UI path, just recommends reviewing existing "draft" content (which the file already says lands as drafts) before publishing.

### Q26 — Meta Business Account phone-number limit blocks a new WhatsApp connection (GAP)
**File:** `kb/case/whatsapp-messenger-issues.md`
**Where:** new subsection after "WhatsApp Not Working After Connection."
**Why:** The file's checklist (Business Admin role, number not in use elsewhere, verification pending, popup blockers) doesn't cover the case where **everything on the checklist is correct** but Meta's own per-Business-Account cap on phone numbers is the actual blocker. This is an external Meta platform limitation (not a Chatty setting), so it's safe to document without inventing any internal UI path — the fix is entirely on the Meta/WhatsApp Manager side (free a number slot or request a higher limit from Meta).
