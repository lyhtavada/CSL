## Cần bổ sung (PARTIAL)

### Q1 — `kb/reference/getting-started.md` § "Wishlist page is blank"
Current file lists 3 causes (nav menu missing, app embed off, hidden content block on default template) — none of them cover the case where the merchant is simply viewing the wrong page (a manually created page at a different handle than the app's auto-generated `/pages/joy-wishlist`). Session 0 this window confirmed this exact root cause: merchant's page was at `/pages/wishlist`, and the fix was pointing them to the real generated page.
**Fix applied in payload:** added a 4th numbered cause referencing the page-handle check, cross-linking to `ref_wishlist-design` § Wishlist Page.

### Q2 — `kb/reference/wishlist-design.md` § "Wishlist Page"
The file already documents that the Wishlist page is locked to `/pages/joy-wishlist` and can't be embedded on a separate custom page — but that note is framed around "can I move the wishlist to my own page" (a feature question), not the symptom a merchant actually hits when a menu item or link references a stale/incorrect page handle and gets a 404. Session 4 (French) this window is a direct example: the store's menu link pointed at `/pages/pages-joy-wishlist-1`, which resolved to the site's FAQ page instead.
**Fix applied in payload:** added a new paragraph immediately after the existing locked-URL note, describing the 404 symptom and the fix (check Content → Pages for the real handle, update the link; team creates a new page if the original can't be found).

### Q6 — `kb/reference/wishlist-design.md` § "Wishlist Access → General settings" (custom icon upload)
The file documents the recommended custom-icon spec (1:1 ratio, <200kb) but doesn't call out that an icon can be uploaded correctly and still appear "missing" because it blends into the header background color — confirmed in session 8, where the actual root cause (found by human agent Rosie inspecting the storefront) was a dark icon on a matching dark header, not a bug.
**Fix applied in payload:** added a short note directly after the custom-icon spec sentence, framing this as a contrast issue to check before escalating as a display bug.

### Q13 — `kb/reference/translations.md`
The file correctly documents where to edit text (Wishlist Design for default language, Settings → Translations for others) but has no troubleshooting note for "I edited it correctly but the live site still shows the old text." This window had two real cases: session 18 resolved via a browser cache clear, session 15 turned out to be a genuine backend bug (system falling back to default text) that the dev team fixed.
**Fix applied in payload:** added a new "## Edits not reflecting on the live storefront" section (cache-first, then escalate-if-persists) before "## Share-link domain".
