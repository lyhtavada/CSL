## Cần bổ sung (GAP/PARTIAL)

### Q2 — Floating button that isn't from Joy Wishlist at all
**File:** `kb/case/hide-wishlist-icon.md`

**What's there today:** covers disambiguating which of Joy Wishlist's *own* 4 icon types a merchant means (header icon / floating button / button on thumbnails / button on product page). It does not cover the separate scenario where the element the merchant is pointing at isn't from Joy Wishlist at all — it's theme-native or from another app.

**Real case this window (session 2):** merchant asked to remove a floating button from their homepage, assuming it was Joy Wishlist's. Agent confirmed the store's actual Joy Wishlist heart icon was working fine, and after checking Apps and the theme, confirmed the floating button in question was built into the theme, not the app — required a full round-trip (asking merchant to check installed apps, then escalating to tech to confirm) before landing on the answer.

**What to add:** a short diagnostic subsection so agents can front-load the "is this even ours?" check before disambiguating *which* app icon it is — e.g. "Joy Wishlist's floating button is heart-shaped and toggled under Wishlist Access; if what the merchant describes looks different, check Shopify Admin → Apps for another wishlist app first, then treat it as theme-native if none is found."

**Priority:** Medium — single session this window, but this kind of misattribution costs multiple round-trips (~5+ messages) each time it happens; worth a short preemptive note.

### Q11 — Feature request: auto-apply Wishlist Button to all product templates
**File:** `kb/reference/wishlist-design.md`, § "Not yet available"

**What's there today:**
> - Multiple named/categorized wishlists.
> - Cart-abandon-to-wishlist prompt — on roadmap; any date given was merchant-specific, don't generalize.
> - "Notify me when available" instead of Add to Cart for out-of-stock items — explicitly declined, not feasible.
> - Lazy-loading/deferred load of the widget — explicitly declined for technical reasons.

Doesn't include the "block must be added to each product template individually" limitation as a known/roadmap item, even though `case_wishlist-button-not-showing.md` already documents the limitation itself. This is about capturing it as a *logged feature request*, not just a troubleshooting note.

**Real case this window (session 8):** merchant with a catalog that changes every 2–3 months pushed back hard on having to manually add the button to every product template, calling it not scalable and saying "I don't feel that is helpful for ecommerce."

**What to add:** a bullet under "Not yet available": *"Automatic Wishlist Button placement across all product templates (currently requires adding the block to each template individually via Theme Editor, see `case_wishlist-button-not-showing`) — logged as product feedback, no ETA."*

**Priority:** Medium — one session this window, but it's a merchant-facing complaint about a structural limitation likely to recur as more multi-template stores onboard.

### Q14 — Manually setting/overriding a product's wishlist count
**File:** `kb/reference/analytics.md`

**What's there today:** § "Per-product analytics" only addresses *reporting* — that there's no per-product wishlist-count report on the Dashboard, with Export CSV as the workaround. It doesn't address whether the count itself (the number shown on the storefront / used in analytics) can be manually written to or overridden.

**Real case this window (session 7, Chinese-language chat):** merchant asked directly whether they could set a custom wishlist count for a product from the backend (e.g. set Product A to show "100" wishlists), then said their dev team had built code to change the value and asked if it would be compatible with the app. Agent correctly said no manual-override feature exists and that counts are auto-tracked from real customer behavior, but the answer isn't documented anywhere in the KB, and the "is custom code compatible" follow-up was left open (forwarded to team, no resolution in-window).

**What to add:** a new subsection in `analytics.md`, before or after "Per-product analytics": *"Wishlist counts (both per-product and Dashboard store-wide totals) are always calculated from real customer wishlist actions — there is no admin field or setting to manually set, preset, or override a product's count. Custom code that attempts to write to this value isn't officially supported; treat compatibility requests as needing tech-team review, not a yes/no the agent can confirm directly."*

**Priority:** Low — single session, low-frequency topic, but a clear-cut yes/no answer worth codifying so agents don't need to reason it out live (and so no agent ever mistakenly confirms compatibility with unsupported custom code).
