## PARTIAL detail

### Q6 — Background color field doesn't support transparent
**File:** `kb/reference/wishlist-design.md`, § "Styling & CSS customization limits" (also relevant: § Wishlist Access → General settings, § Wishlist Button General settings)

**What's there today (verified from cached file):**
> Color and icon are adjustable via the **General settings** section on Access/Button tabs; button text has its own **Button text** section on the Button tab (see § Wishlist Button above). For anything beyond that — border-radius, spacing/margin, font sizing, icon/image size, image cropping on the wishlist page — collect the exact spec (e.g. size in px, which icon/element) and pass it to the team to apply; **no collaborator code needed for this.**

This covers "beyond the UI" styling generically, but doesn't call out the specific, repeatedly-hit gotcha: the **Background color field itself only accepts solid colors** — merchants setting it to white while trying to get a "border only" outline look end up with an invisible icon (white-on-white), and don't realize transparency isn't an option until they test it. Two sessions this window hit exactly this (session 1: homepage product-card icon; session 6: header icon) — same underlying field limitation on both Wishlist Access and Wishlist Button General settings.

**Correct/complete line to add:** the Background color field on both Access and Button General settings only supports solid colors — no transparent/none value. A transparent-background look requires custom CSS from the team (same "no collaborator code needed" process already documented).

**Priority:** Medium — small, low-frequency (2-3 sessions/window) but the same gotcha appears in both mines now (this run + prior run's Q7 in the Dec–Jul backfill), so worth codifying instead of re-discovering each time.
